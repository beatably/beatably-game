# Beatably iOS — Release Guide (App Store submission)

Step-by-step for cutting a new version of the iOS app and submitting it to the
App Store. Follow top to bottom. Companion doc: [APPSTORE_LISTING.md](APPSTORE_LISTING.md)
holds all the copy-paste store metadata (description, keywords, What's New, review notes).

**Key facts about this project (why some steps look unusual):**
- The Xcode project is **generated by xcodegen** from [`project.yml`](project.yml). `Beatably.xcodeproj` and `Beatably/Info.plist` are **git-ignored build artifacts** — never edit them by hand, edit `project.yml` and regenerate.
- **Version** (`CFBundleShortVersionString`, the user-facing "1.1") comes from `MARKETING_VERSION` in `project.yml`. Bump it manually per release.
- **Build number** (`CFBundleVersion`, e.g. "279") is **auto-stamped from the git commit count** at build time by a pre-build script. You never set it by hand — but it means **the build number is only final once you've committed**. Commit before you archive.
- Bundle ID: `app.beatably.ios`. Deployment target: iOS 17.0. Scheme: `Beatably`.
- Signing is **automatic**, configured in the Xcode UI — it is **not** in `project.yml`, so it can reset when the project is regenerated (see Step 3 gotcha).

---

## 0. Decide the release

- [ ] Pick the new version number (e.g. `1.1` → `1.2`, or `1.1` → `2.0`). Follow semver-ish: bug-fix/minor tweaks bump the minor, big changes bump the major.
- [ ] Write the **"What's New"** text (user-facing changelog for this version). Draft it in [APPSTORE_LISTING.md](APPSTORE_LISTING.md) under the version's section.
- [ ] Confirm the code you want to ship is committed and, for the web/backend half, deployed (`git push` → Netlify + Render auto-deploy). The iOS build should point at the production backend.

---

## 1. Bump the version

In [`project.yml`](project.yml), update:

```yaml
MARKETING_VERSION: "1.2"   # <- new user-facing version
```

That's the **only** version field you touch. Leave `CURRENT_PROJECT_VERSION` alone (the git-count script overrides the real build number).

- [ ] `MARKETING_VERSION` bumped in `project.yml`.
- [ ] Update the "Version info" + "What's New" sections in [APPSTORE_LISTING.md](APPSTORE_LISTING.md).

---

## 2. Commit the release changes

The build number is the git commit count, so **commit first** — otherwise the number you archive won't match `main`.

```bash
cd /Users/tim/Game
git add -A
git commit -m "release: iOS <new-version>"
git push origin main
```

- [ ] Version bump + any release code committed and pushed to `main`.
- [ ] Note the resulting build number: `git rev-list --count HEAD`.

---

## 3. Regenerate the Xcode project

```bash
cd /Users/tim/Game/ios
xcodegen generate
```

- [ ] Project regenerated (`Created project at .../Beatably.xcodeproj`).
- [ ] If Xcode is open, close and reopen `Beatably.xcodeproj` (or "Revert" when it prompts that the project changed on disk).

> ⚠️ **Signing gotcha:** because the `.xcodeproj` is regenerated and signing isn't stored in `project.yml`, the **Team** selection can reset. Open the project → target **Beatably** → **Signing & Capabilities** and confirm **"Automatically manage signing"** is on and your **Team** is selected. Fix it here before archiving if it's blank.

---

## 4. Verify version & build number before archiving

Quick sanity check that the About screen will read correctly (build for the simulator; no signing needed):

```bash
cd /Users/tim/Game/ios
xcodebuild -project Beatably.xcodeproj -scheme Beatably \
  -sdk iphonesimulator -configuration Debug \
  -destination 'generic/platform=iOS Simulator' clean build

PLIST="$HOME/Library/Developer/Xcode/DerivedData/Beatably-*/Build/Products/Debug-iphonesimulator/Beatably.app/Info.plist"
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' $PLIST   # -> your new version
/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' $PLIST              # -> git commit count
```

- [ ] Version string matches the new `MARKETING_VERSION`.
- [ ] Build number matches `git rev-list --count HEAD`.

(In the app, the version is shown at the bottom of the **How to Play** screen.)

---

## 5. Archive in Xcode

1. Open `Beatably.xcodeproj` in Xcode.
2. Set the run destination to **Any iOS Device (arm64)** — the top device selector. (You cannot archive with a simulator selected.)
3. Select the **Beatably** scheme.
4. Menu: **Product → Archive**.
5. Wait for the build; the **Organizer** window opens automatically when it finishes.

- [ ] Archive succeeded and appears in **Window → Organizer → Archives**.
- [ ] The archive row shows the correct **Version** and **Build**.

> If Archive is greyed out, the destination is still a simulator — switch to **Any iOS Device**.

---

## 6. Upload to App Store Connect

In the **Organizer**:

1. Select the new archive → **Distribute App**.
2. Choose **App Store Connect** → **Upload**.
3. Accept the defaults for symbols/signing (automatic). Let Xcode manage signing.
4. **Upload**. Wait for "Upload Successful".

- [ ] Upload succeeded.
- [ ] Wait ~5–30 min for the build to finish **processing** in App Store Connect (you'll get an email; until then it won't be selectable on the version page).

> **Export compliance:** `ITSAppUsesNonExemptEncryption` is already set to `false` in `project.yml`, so App Store Connect should **not** ask the encryption question. If it ever does, the answer is **No** (the app uses only standard HTTPS).

---

## 7. Fill in the version in App Store Connect

Go to [App Store Connect](https://appstoreconnect.apple.com) → **Apps → Beatably**.

1. Click **" + "** next to iOS App (top-left) → **create a new version** → enter the new version number (must match `MARKETING_VERSION`).
2. On the version page, fill in from [APPSTORE_LISTING.md](APPSTORE_LISTING.md):
   - [ ] **What's New in This Version** (required for every update).
   - [ ] **Promotional text** (optional, editable anytime).
   - [ ] Confirm **Description** / **Keywords** (only change if they changed).
   - [ ] **Screenshots** — reuse the existing 6.9" set unless the UI changed. Source: `ios/screenshots/appstore/6.9/` (fallback 6.5" set in `.../6.5/`). See the "Screenshots" section in APPSTORE_LISTING.md for slot/order.
3. Under **Build**, click **" + "** / **Select a build** and pick the build you just uploaded (it must have finished processing).
4. **App Review Information** → paste the reviewer notes from APPSTORE_LISTING.md (the notes explain how to test full gameplay solo on a single device — important, keep them current).
5. Confirm **Copyright**, **Support URL**, **Age rating** if anything changed.

- [ ] Version created, metadata filled, build attached.

---

## 8. Submit for review

1. Choose the release option (usually **"Automatically release this version"** after approval, or **Manually release** if you want to control timing).
2. Click **Add for Review** → **Submit for Review**.

- [ ] Submitted. Status → **Waiting for Review**.

Typical review time is ~24–48h. You'll get email updates. If **rejected**, read the Resolution Center message, fix, and re-submit (usually no need for a new build unless the issue is in the binary — but if you do rebuild, repeat from Step 2 so the build number increments).

---

## 9. Post-release

- [ ] Once **Ready for Sale**, verify the update appears on the App Store and installs.
- [ ] Tag the release (optional): `git tag ios-v<version> && git push --tags`.
- [ ] Update project memory / notes that the version shipped.

---

## Troubleshooting

| Symptom | Cause / Fix |
|---|---|
| About screen shows **build number `1`** | You edited the built product plist by hand, or an old script. The build number is stamped from git by the pre-build script in `project.yml`; regenerate (`xcodegen generate`) and clean-build. Don't hand-edit `Info.plist` (it's git-ignored/generated). |
| **Version** is wrong / stuck on an old number | `MARKETING_VERSION` in `project.yml` not bumped, or project not regenerated. Bump it, run `xcodegen generate`, rebuild. The plist reads `$(MARKETING_VERSION)`. |
| **Archive** menu item greyed out | Run destination is a simulator. Switch to **Any iOS Device (arm64)**. |
| **Signing errors** on archive | Team reset by `xcodegen generate`. Target → Signing & Capabilities → re-select your Team, keep "Automatically manage signing" on. |
| Build **not selectable** in App Store Connect | Still processing (wait for the email), or missing compliance. Give it 15–30 min. |
| "**This build has an invalid version / already exists**" | Build number must be unique & increasing. Since it's the git commit count, just make one more commit and re-archive — the number will bump. |
| Uploaded but wrong build number in ASC | You archived before committing. Commit, regenerate, re-archive (Step 2 onward). |

---

## One-glance summary

```
1. Bump MARKETING_VERSION in project.yml + write What's New in APPSTORE_LISTING.md
2. git commit && git push          (build number = commit count, so commit first)
3. cd ios && xcodegen generate     (check Signing & Capabilities → Team)
4. (optional) simulator build to verify version/build strings
5. Xcode: Any iOS Device → Product → Archive
6. Organizer → Distribute App → App Store Connect → Upload
7. App Store Connect → new version → paste metadata + attach build + reviewer notes
8. Submit for Review
```
